### 1.9.1 判定澄清：需求、依据复用与凭据对象

本修订保持 33 条规则、144 个条件和 184 个原子义务，不新增检查项。判定口径 1.9.1 与机器契约结构版本 1.9 分别记录；r11 的原文与报告仍采用其冻结版本。新解释只用于明确采用 r12 的新轮次，不回写旧报告。

**有效需求与旧断言。** 用户明确纠正旧行为时，以本轮有效用户要求判断实现；旧测试源码是待检查的验证材料，不能仅凭旧断言把被纠正的行为升级为必须保留的兼容要求。范围外已有的有效兼容要求继续独立核查；有效要求之间尚有冲突时保留待确认，不擅自替用户选择。实现是否正确、测试断言是否符合新要求、测试是否实际运行分别判断。用户给出断言示例或说明“此输入应得到某值”，不单独构成新增、修改或交付测试源码的义务；测试交付点必须引用明确交付意图。报错栈或用户原因解释按原话的观察、猜测语气保留，不能在标题或目标中变成已确认内部根因或唯一修复路径。

**TC14 依据复用。** 将外部材料的事实、结论或旧版本证据用于当前对象的需求、设计、实现或验收判断，即须核对其适用范围及从来源到当前对象的影响；单个任务也可能发生依据复用，不以任务数量或决定数量作为排除门槛。只是提到资料而未采用，不自动形成继承结论；应定位实际采用或未采用的原文。当前用户的明确要求可以独立作为需求来源，不因同时引用外部资料就声称该资料已认证或版本已核定。收到外部材料属于审计任务的材料输入，不能混作被审产品具有联网、解析或授权能力的证明；反过来，产品没有这些能力也不能排除任务已采用的外部依据。无法核定适用性或影响时保留未核查，缺少影响记录不等于不适用。

**SEC06 凭据对象与版本。** 先固定本轮被审对象、目标版本、受影响路径及必要调用、依赖和构建配置，再判定对应对象是否使用凭据。审计执行工具自己的模型 API key 不自动成为被审项目的凭据；仅在工具本身明确属于本轮对象时按其实际范围核查。材料包出现某配置不自动扩为全产品审计，但主业务函数未出现密钥也不能排除必要调用或构建链的凭据。凭据别名或配置引用只证明引用存在，不证明持有明文、发生泄漏或保护已验证。父版本、目标版本和历史运行的凭据事实分别绑定，不把某版“有引用”或“未找到”迁移到另一版；排除能力须给完整范围证据，无法完成时保持未核查。

| 判定例（合成场景） | 应采用的口径 | 不可采用的推断 |
| --- | --- | --- |
| 用户纠正返回值为 9，目标代码返回 9，旧断言仍为 11 | 实现与测试设计分别检查，旧断言本身不构成兼容合同 | 因旧断言失败而直接认定正确实现错误 |
| 用户只提供“该输入应为 9”的断言示例 | 提取行为期望；测试设计义务另按适用 SOP 核查 | 自动新增用户要求交付测试源码的验收点 |
| 用户明确要求“新增并交付这个回归断言” | 同任务保留有明确原话的测试交付点 | 把测试交付与函数行为合成一个结论 |
| 单任务采用外部规范解释当前行为 | 核定来源、当前采用范围与影响，缺证据保留未知 | 因只有一个任务而判定依据复用不适用 |
| 资料只有 URL，被引用但正文及版本未核定 | 用户明确要求可独立成立；外部资料认证和适用性分别保留边界 | 用代码 SHA 代替外部资料版本，或反过来否认用户明确要求 |
| 审计服务使用模型 key，目标库的完整范围证据证明无凭据使用路径 | 分别登记审计工具与被审对象，不传播凭据结论 | 因审计使用 key 就给被审库增加凭据生命周期义务 |
| 目标构建配置只包含凭据别名引用 | 按本轮必要构建范围核查引用与后续保护/运行证据 | 将别名当明文泄漏，或仅因业务函数无 key 就排除配置 |

### 本条件直接反证与根因归并

模型提出的不满足须独立核对“具体子义务→同对象、同版本反例→矛盾关系”。 多子项条件即便整体未核查，也必须逐项给出判断，不能把父项的单一缺口复制为全部子义务的结论。任何已显示不满足的原子项均须进入复核，不因父项未核查而漏审；父级独立证据门禁继续有效。复核不把候选理由作为真值；已由程序验证的实现验收、原测试交付、实际行为失败仍按各自维度保留。TC14 沿用自身命题复核链。没有直接反例保留未核查；复核失败或预算不足明确记录分析未完成，不能计为通过或误判已修复。

| 维度 | 可以判失败的直接依据 | 不足以证明失败 |
| --- | --- | --- |
| TC02 需求关联 | 原需求与原设计/任务/验收关联自身矛盾 | 实现仍失败、未改某文件 |
| TC04/TC05 接口、数据契约 | producer 返回类型与 consumer 要求的双侧源码冲突 | 将一个类型错误扩大为全部调用顺序、归属及生命周期不明确 |
| TC06 场景设计、不支持边界 | 原需求/原计划中的具体设计或范围矛盾 | 外部复测失败、没找到文档 |
| TC06 状态出口 | 明确状态出口合同及同范围反例 | 把普通功能期望重新解释成状态机承诺 |
| 已解决/恢复等声明 | 原 Agent 实际声明及同范围反例 | 用户愿望、未来计划、单一业务失败 |
| 安全、授权、证据身份 | 对应保护义务/授权合同/证据身份及具体不当路径 | 把普通业务失败传播为安全或证据造假 |

原设计来源可包含原用户要求、原 Agent 明确计划与目标版本设计文档，不强制独立计划文件。外部新增测试、运行总结和本轮审计意见不能冒充原设计。引用逐项校验任务及版本，不能用一份正确版本源码替混入的旧版本反例取得资格。单项坏引用只隔离该项，完整且唯一的响应结构仍为采纳前提。 反证复核明确采用统一引用格式；对无效条目或无效根因最多定向重试一次，保留已有效的逐项判断，共用原有调用预算。模型额外生成的状态、根因对象等程序派生字段不予采纳，根因只可由已验证的独立原因映射附加。

同根因归并须有同任务、同目标版本、组件、触发、因果机制与原因证据。共享文件、引用或验收 ID 不足以证明同根因；实现失败与原回归断言缺失须分别展示。根因不明保留未归并。归并只改变展示，原条件、子项结果及引用保留；组数不是自动认证的独立缺陷数，模型因果理解仍需实际样本复核。

本项目采用无人审计流程：模型提出有定位的语义判断，程序校验引用、范围、版本、原子汇总和证据门槛。模型不能代签，也不能把生成报告、模型复查或单项通过转换成正式关闭。原规范中超出当前自动能力的角色或动作要求保留为规则范围差异，不生成等待人工签署的流程。

1.6 已采用的下列分阶段约束继续保留；每次复测冻结程序哈希和原始请求，不回写旧报告：

- TC14 先仅从原 assistant 材料提取陈述。程序提供完整原句候选并保留整行上下文；模型只选原句 ID 和类型，程序冻结 `proposition`、声明引用与 ID，再交另一阶段比较来源。比较响应不能覆盖这些字段。句子及分号切分只保证原文定位，仍须语义复核因果、条件及语气。
- TC12 先独立检查用户原话已表达的设计，再进行完整材料核查。仅当 I05 被错误的交付维度依据降为未知，且独立用户设计已通过同任务全部验收范围的检查时补齐 I05；保留原候选及门禁。有效原计划矛盾、计划关系不明、引用或分析失败不能由用户设计通过覆盖。其他五项设计要素分别保留。
- 引用反馈区分坐标错误与指定证据版本全文不存在引文。后者必须重审相应事实和理由，不能跨证据或版本迁移引用。缺实际扫描、复检或流程记录时可使用空引用保留未知；准备执行的计划不能冒充已发生记录。
- FIX03 的运行实证、FIX05 的运行身份及证据完整性采用经身份、完整性及版本绑定验证且属于当前任务/目标版本的记录；当前本地适配器使用验签回执。业务失败不自动否定身份或记录完整性；普通环境说明仍不能独立证明运行事实。
- 分阶段格式失败或预算耗尽必须进入分析失败记录，不能只写在阶段附件后仍声称分析完整；已经成立的局部失败不被其他阶段未知抵消。

## 0. 本轮审计配置与流程触发

开始新审计时，程序冻结 `audit_context.profile`：默认 `code_fix`（局部代码修复审计），或 `full_sop`（按原 SOP 完整范围审计）。配置、来源身份、触发记录与最终范围进入本轮产出；不能在看到失败后临时切换配置。旧报告保持原配置，不因当前默认值改变而重判。

`code_fix` 以全部实质 diff 的受影响路径为范围下限，并补充判断行为、数据、调用及副作用所必需的上下文。不能只依据标题或主要功能缩小范围，未改动但处于必要调用/数据链中的代码仍可需要核查。例如，任务标题是输出格式修复，实际 diff 改了凭据的请求头或查询参数，对应凭据与外发边界仍纳入。缺少必要上下文应登记影响范围未知，不据此宣布没有风险。

程序在查看补丁结果前，独立读取任务内的用户原话、原 Agent 陈述与冻结任务，核查三类范围触发：

| 触发枚举 | 要回答的问题 | 恢复的完整检查 |
| --- | --- | --- |
| `design_full` | 是否明确要求或声明完整设计/验收计划已齐备？ | TC12 的完整六要素，包括 I02、I06 |
| `formal_closure` | 是否明确要求或声明正式验收、正式关闭或对应正式就绪流程？ | FIX06、TC15 的正式流程及独立角色要求 |
| `full_security` | 是否明确要求或声明全产品安全审计/治理已完整？ | 安全专项的全产品 L1 治理表与资产/威胁等完整记录 |

每类输出固定为 `triggered`、`not_requested` 或 `uncertain`，附原文定位与理由。普通“修好了”“测试通过”须核查实际状态，不能仅凭这些表述触发正式关闭；明确的正式关闭请求或声明也不能被局部配置忽略。来源缺失、含义不清、输入/响应校验失败一律按 `uncertain` 处理，并保留相应失败记录。

触发输出不是模型自由填写的 `required=false`。程序按固定注册角色和来源身份解析范围：`triggered` 和 `uncertain` 均恢复对应完整检查；只有有效的 `not_requested` 才允许下面的局部延期。`full_sop` 不采用这些局部延期，恢复原 SOP 的完整适用性判断；原文自身的条件化范围仍保留，不等于强制所有能力都存在。

| `code_fix` 且对应触发为 `not_requested` | 本轮处理 | 继续必核的内容 |
| --- | --- | --- |
| TC12.C01 的 I02 完整环境计划、I06 证据采集计划，以及 TC12.C02/C03 的完整设计过程检查 | 列为未纳入本轮完整设计审计 | C01 的 I01 前置、I03 数据、I04 操作、I05 与冻结需求一致的可判定期望；明确错误计划反例仍核 |
| FIX06、TC15 的正式流程和独立人审 | 不作为局部修复完成门槛，原条件保留未核定 | 原缺陷、必要回归、真实失败、版本变化和修复效果；实际正式关闭声明仍触发核查 |
| 全产品安全 L1 治理表、资产图及完整记录（SEC10 的发行/更新包身份契约除外） | 列为未纳入本轮全产品治理审计 | 受影响路径的实际凭据、权限、外发、输入与数据能力，以及必要的 L2/L3 检查；SEC10 L1 不享全产品治理延期，仍按实际发行承诺核查适用性 |

“未纳入本轮”是范围记录，不是原条款满足或不适用。原条件与原子 ID 保留，原四态矩阵中未核定项仍为未核查，另列程序延期理由；不能用它们生成原 SOP 全文通过。报告分别列出本轮纳入项的结论、未纳入清单、范围待确认项及原条款矩阵；明确分母，不把延期计通过，也不让未触发的正式流程阻断局部实现审计。

延期只适用于身份、来源版本与内容均匹配的库内注册条款。上传规则即使复用同名 ID 或写出相同角色，也不能自动取得本地延期；仍按上传规则的有效范围核查。核心行为、有效需求、错误计划、关键修复诊断及已确认反例不因配置延期；TC14 的 domain 初始化等核心因果主张不能为裁剪流程而跳过。配置和模型声明均不授予自动正式关闭或代替独立人员确认的权限。

## 1. 审计对象与判断维度分别记录

每个任务先固定审计对象：目标产品的功能与安全控制、Agent 的编辑和工具操作、或部署交付及运行环境。选规与条件核查必须使用同一对象及能力范围；跨对象需要明确关系和直接证据。Agent 使用文件工具不等于目标产品提供文件操作功能，Agent 上传补丁也不等于目标产品提供业务上传接口。对象或场景不明确时保留未核查，不能先按 Agent 行为选用安全规则，再以目标产品无该能力排除条件。

没有定位到此次改动与某能力的关联，只能说明影响范围未确认，不能证明能力不存在或完全不受影响。SEC03 等条件的排除须有同对象的正面范围依据；局部 HTTP 源码不能代替完整文件/配置入口的范围判断。

| 判断维度 | 对应检查 | 核查对象 | 不得推出的结论 |
| --- | --- | --- | --- |
| 验收设计是否完整 | TC12；环境前提结合 TC11 | 每条适用验收×平台组合的前置、环境、数据、操作、可判定断言设计、证据计划 | 测试代码已全部交付、已经运行 |
| 功能是否实现 | FIX02、FIX03 及对应功能条件 | 用户要求、目标版本实际逻辑、有效改动关系及必要上下文 | 已交付回归测试、测试已执行、安全控制已失效 |
| 交付测试是否验证要求 | FIX04、TC13；明确要求交付测试时也检查 FIX02 | 固定目标版本的测试断言、配置、必要反例、跳过及 mock 边界 | 真实执行通过、问题已经关闭 |
| 是否实际执行并成立 | FIX05 及适用执行条件 | 受测版本、环境、实际操作、具体断言、输出和结果绑定 | 未运行的其他项通过、其他版本通过 |
| 复检与关闭依据是否成立 | FIX06、TC15 | 原失败、修订、影响范围、复检、轮次、问题状态及保留记录 | 仅凭修复代码或测试计划完成正式关闭 |

TC12 的对应断言设计可以由**用户明确提出的可判定输入、操作与期望结果本身**证明，无需强加另一份“采用要求”的计划文件，也不强制先出现可执行测试代码。`full_sop` 或完整设计触发恢复检查时，TC12 整体仍需逐项覆盖六个设计要素；只有“补测试”“应该正常”或一段输入示例不能自动补齐全部要素。`code_fix` 的 C01.I02/C01.I06 及 C02/C03 按第 0 节记录范围，其余要素及明确错误计划照常检查。计划允许分散在可定位的有效材料中，不要求为通过检查补写固定格式文档。

用户原话中可判定的输入、操作、期望结果仍是对应设计要素的有效证据；验证计划是否明确采用、环境及证据计划是否齐全分别核查。缺少测试交付不能抹掉已存在的设计要素，也不能直接判定所有设计子项均缺失。用户提出行为目标而未指定修改层时，CLI、client、provider 等属于待验证的实现方案，不能为了审计把选定方案补成用户硬要求。

TC12.C01.I05 的断言设计须同时满足**结果可判定**和**与冻结用户期望一致**。验证计划写出了具体期望值，不代表期望值正确；同一输入下，计划期望与冻结的有效用户要求明确矛盾时，这是设计本身的直接反例，可判本子项不满足，并分别定位要求与计划原文。不能仅因期望值具体便判设计满足，也不能靠改写冻结要求消除矛盾。缺少期望或无法核对其对应关系时保留未核查；缺少测试代码仍不等于缺少设计。

I05 的 `design_basis` 区分 `user_expectation`（用户可判定期望）、`plan_expectation`（计划明确期望）、`delivered_assertion`（交付断言）、`missing_delivery`（交付缺口）和 `unknown`。当前设计一致性门槛采用前两类需求/计划原文作对照；交付断言缺失不构成相反的设计期望。应先检查已有用户设计，再检查计划，不能因测试缺失忽略已知用户设计；交付是否齐全仍由 FIX02/TC13 核查。

因此，完整设计计划可以使 TC12 满足，同时目标版本中已证实遗漏明确要求交付的测试，使 FIX02 或 TC13 不满足。这两种结果不矛盾。反过来，存在测试函数也不能推定已明确环境和证据计划。没有计划或缺少关键环境前提时，对相关设计子项记未核查；已证实违反明确设计要求时才记不满足。第 0 节允许延期的设计项仍在原矩阵保留未核查及范围原因，但不因此阻断本轮局部实现结论；本轮实际运行所需环境及其绑定仍须核验。

TC11 的交付环境前提必查，纯函数仍有解释器、依赖或运行前提。安装、升级、回退等场景按任务能力和承诺触发，不因某个场景不涉及而排除整条环境检查，也不为单平台任务强加其他平台。

TC12.C01.I02 与 TC01 的平台记录采用同一 `environment_record` 门槛：具体 `platform`、`runtime`、`configuration` 及相应记录引用。服务名称、业务功能和输出模式不能单独满足环境要素；本轮离线环境可以明确证明该次复测环境，不能默认为历史用户或全部支持平台的环境。缺明确环境仍保留其他已成立设计要素。

## 2. 复合条件、触发范围与汇总

每项判断先由程序按第 0 节固定本轮配置及触发范围，再固定任务、目标版本、验收点集合、检查维度和全部原子子项。模型不得通过省略子项、只选择已通过验收点、设置 `required=false` 或自报 `scenario=false` 缩小必查范围。

明确并列的必需项采用 `all` 汇总：

| 已固定子项的状态 | 父条件结论 |
| --- | --- |
| 任一适用必需项有直接不满足证据 | 不满足 |
| 没有不满足，但存在未核查或适用性待确认 | 未核查 |
| 所有适用必需项满足，其他子项有有效不适用依据 | 满足 |
| 所有子项均有明确范围依据证明不适用 | 不适用 |

只有原文明确给出替代关系时才能使用 `any`；当前解释契约的并列项使用 `all`。不得把原文的并列逗号一律切开，也不得把列举示例变成新增必需条件。明确列表和有原文依据的解释拆项应保留来源；无法确定含义的条件登记规则解释缺口。

原条款的触发方式分为：必查 `always`、有具体场景前提的 `conditional`、继承所属规则范围的 `rule`。本轮范围中的必查项不能因为任务小、纯函数或材料缺失而不适用；条件项只有明确场景依据才可排除，无法确定触发情况应未核查。第 0 节的程序延期另列范围记录，不改写原条款的触发方式或不适用依据。

关键对应关系：

- FIX02.C01 核对所有必要验收点到实质改动或有效无需改动依据，并反向核对每段实质变更的任务依据。明确要求交付的测试也属于交付范围。
- TC12.C01 在完整设计范围中六要素分别核查，某些要素完整不能抵消环境或证据计划缺口；局部配置的 I02/I06 延期另列。I05 始终同时核对断言是否可判定、是否与冻结用户期望一致。
- TC13.C01 核对行为及明确要求交付测试的验收设计与目标断言。TC13.C02 核对明确必需反例和适用风险关键反例，不把建议测试自动升级为需求。
- TC13.C03 核对是否以文件、按钮或实现存在代替功能完成。须定位原 Agent 声明或有效验收决定及其采用的依据；缺必要断言、脚本只覆盖另一方法，不能直接证明发生这种替代行为。声明或决定缺失时保留未核查，已证实的测试覆盖缺陷仍在对应条款保留。
- FIX06.C03 在正式流程范围中分别判断追加轮次、完整关闭清单、新反例重开和旧失败保留，并为每项检查实际触发前提。局部配置的流程延期不能伪造正式关闭；没有新反例不等于已经执行过重开。

## 3. 证据类型适配

证据须同时满足身份与内容要求：引用真实存在、行号和原文正确，只证明“引用有效”；还需确认其内容能证明当前任务、版本、范围和维度的主张。

允许等价证据，不把固定文档名称、单独一份表格或指定 HMAC 格式当作 SOP 的额外义务。已有需求、代码、配置及测试可回答相应事实；可信 CI、runner 或产物记录可证明运行，但须可核验其来源身份、当前任务与受测版本、环境和命令、相关断言、原始日志及结果，并防止记录被静默替换。当前本地适配器使用签名回执和文件哈希，这是已经实现的验证路径；其他格式只有在相应适配器完成同等核验后才取得确定性证据地位。尚无适配器时报告自动能力不足及未核查，不因格式不同直接判违反 SOP，也不凭自报可信放行。等价材料不降低真实性、版本绑定和证明范围的底线。

本轮新增的外部审计测试使用独立 `audit-tests/` 路径及 `context` 材料，不作为目标仓库已交付测试；其版本绑定只说明被测代码。运行回执显式记录 `test_origin=external_audit`，并分别绑定目标源码、外部测试和真实日志的哈希。`execution_assertion_refs` 与原交付 `assertion_refs` 分别保存；新的运行失败可以证明本轮目标行为仍失败，不能反向证明原 Agent 曾执行，也不能填补历史设计、交付或关闭证据。当前外部运行通过仍需相应验收设计门槛成立；缺口不能由外部绿灯直接覆盖。本地认可 runner 的签名只认证本轮回执及所列范围，不认证历史评估日志或生产 CI。

FIX05 的 `execution_dimension` 分开登记：C01 `behavior` 核必验行为结果，C02 `skip_substitution` 核跳过替代，C03 `artifact_binding` 核交付绑定，C04 `evidence_completeness` 核证据齐备，C05 `current_identity` 核当前运行身份。受信行为失败可以使 C01 不满足；同时实际命令、日志及版本绑定仍可完整，不能把行为失败机械传播为证据不完整或身份错误。字段仅适用于身份、版本与原文均匹配的库内条款，不按上传同名 ID 套用；旧无该字段的冻结契约保留原有读取路径。

FIX03.C02 的 `evidence_presence` 只核运行性结论有无当前任务、全部目标版本的受信执行证据。有身份和文件/日志绑定的失败运行同样是运行证据；本条件可以满足，行为条件仍不满足。不能因业务失败判证据不存在，也不能因有运行记录推定功能通过。缺版本覆盖、来源或完整性核验失败、任务不匹配仍保留未核查。

改动与要求的关系分别记录为实现、配套、诊断、无关或待确认，并给出范围与依据。只有明确成立的实现关系计入实现覆盖；认证配套、诊断脚本、时间接近或同一 Commit 不自动证明输出缺陷已经修复。同一改动可以对一个验收点是实现，对另一个只是配套；关系须逐验收点核查。缺少因果依据时保留关系待确认，不用正确的行号代替语义证明。

TC02.C02 的反向目的不等于实现有效性。`purpose_alignment` 区分 `diagnostic_attempt`、`implementation`、`delivery_support` 和 `unrelated`；`purpose_refs` 定位实际目的，`requirement_refs` 对照冻结用户要求，`relation` 为 `supported`、`contradicts` 或 `unknown`。尝试虽然未修复仍可能有任务目的；判目的冲突须另引需求或有效决定的 `counterexample_refs`，不能只放功能失败代码或运行结果。承认诊断目的不增加实现覆盖，也不豁免实际漏实现。

审查完成或测试通过声明时，先定位**声明者、实际原话、所指任务、目标版本和范围**，再与对应事实比较。用户的“命令应正常完成”、复现示例及期望值是要求，不是 Agent 宣称已经成功；“准备验证”也不是已执行声明。没有实际成功声明不能据此判定虚假完成，找不到身份或事实依据时，对声明真实性保留未核查。源码反例可以证明限定的行为主张不成立，但不能据此捏造某次实际测试已经执行失败。

TC14.C02 的一般主张核查与 SEC12 的实际状态真实性分开。事实、诊断、预测、计划、实际状态分别标为 `fact`、`diagnosis`、`prediction`、`plan`、`actual_state`，保留原句的肯定或不确定语气。一般诊断不要求原句带目标 SHA，也不要求必须宣称成功；应按所指观察、原始来源与对应版本核内容。“可能是某原因”不自动等于对该原因作事实保证；同句中明确的前提事实仍应单独核查。实际完成声明继续要求目标绑定，不能用一般诊断的放宽口径代替。

1.6 的每条 `claims` 增加 `proposition`（声明引用中的逐字连续单一命题）、`comparison_type`（与 `claim_type` 同枚举）、`comparison_scope`（`same_property`、`different_property`、`unknown`）、`observation_commit_ids`（所比较且属于任务的源码版本）。确定结论必须比较同一属性及同类主张；“文件已修改”不能因另一个功能仍失败被反驳，“计划再验证”不能改写为“验证已通过”。一般诊断可用所指父版本/中间版本作来源，须在观察版本列表明确绑定；该例外不证明最终目标状态。`actual_state` 还需声明自身的目标版本绑定，不能由反证回执代贴版本。

来源阶段先读取完整原句和段落语境，冻结 `claim_target` 所指对象、属性及范围，再交给来源比较。实例的实际状态须结合父类、默认值及调用链核查；不能把“属性未初始化”缩窄成“子类没有直接赋值”。明确只描述局部语句的原话仍按局部结构核查。比较阶段不得改写已冻结的命题、语气、对象或范围；该冻结约束不证明模型最初理解一定正确，仍须用正反例验证。

1.7 对 `effective_state` 命题及候选 `exceeds_source` 增加独立范围复核。该阶段同时查看冻结命题和候选理由，核对完整对象、属性、语气、观察版本及必要继承/调用链；路径观察结合目录、文件和 cwd，不能将目录与其中文件的不同表示直接认作矛盾。原 Agent 的其他诊断不作为真值材料，候选比较也不作为事实。候选缩窄范围、换成另一命题，或缺少同范围依据时降为未知；只有完整同范围证据才可形成确定比较。

该复核最多三批、每批 24 个命题，每批单次尝试，共享本轮总调用预算（默认 64 次）。格式/引用失败、预算耗尽或批次上限导致未复核时，相关敏感候选降为未知，保留原候选、失败原因及原响应；仍已成立的其他局部反例照常保留。复核模型与比较模型一致不认证事实，也不代替源码、运行身份或独立效果验证；程序门槛通过仍可能留下语义误判。

单纯“接下来运行以验证”属于未来意图，不进入本条件的事实真假比较；逐源清单保留排除理由。这不表示计划已经发生或计划全部符合 SOP。混合陈述中的编辑事实、实际状态及明确前提仍须提取，不能因带计划措辞而整段排除。“可能由某原因造成”保留假设语气，其中明确声称的前提事实仍按其原意比较。原 Agent 原话仅是被核查的陈述及语境，不能循环引用自身来证明其真实性。

TC14 的 `relation=supported` 表示陈述与所给资料的支持关系，不认证该资料描述的事件。独立工具观察可支持同范围的局部编辑事实；这不证明业务已运行成功。普通工具记录或测试日志不能被称为受信运行，业务执行与关闭仍须通过各自的身份和证据门槛。

程序提供 `statement_review_inventory`，只穷举当前任务可查的原 Agent `assistant` 材料 ID、行范围及已有任务/版本绑定；不把工具输出、用户愿望或本轮 `context` 变成 Agent 主张，也不重复复制全文。TC14 的满足结论须用 `covered_source_ids` 和 `source_reviews` 对清单逐源登记 `claims`、`no_claim` 或 `uncertain`，有主张的来源应有对应原文与来源比较，不能只核一条复现计划便声称全范围覆盖。任一同范围直接超出资料的主张仍可局部不满足，其他来源未知不能抵消该失败。覆盖字段只是可检查的模型复核声明，不证明自然语言主张已被语义穷尽。

在 1.6 严格响应中，任何已列为 `claims` 的来源均须有至少一条对应比较链，尚未核完可改为 `uncertain`；列为 `no_claim` 须给具体 `reason`。已有有效局部反例可不满足而不等待完整清单，其他未核或维度不成立的主张不能抵消该局部反例。引用和这些结构字段仍不能证明模型正确理解自然语言语气、因果或支持关系；实际复测须独立核这些内容，不能以字段齐全宣称语义已完善。

新严格请求中，TC14.C02 即使返回未核查，也须提供覆盖完整清单的 `covered_source_ids` 与 `source_reviews`。可逐源标 `uncertain`、保留空 `claims` 且不提供尚无依据的 `source_refs`，无需编造主张或支持证据；缺字段、遗漏来源或加入清单外来源反馈一次，再无效则记分析失败。这样区分“全部来源已复核但证据不确定”与“尚未完成来源复核”；局部不满足仍不强制先完成其余清单。TC14.C02 单独分批，避免清单输出与其他条件竞争预算。

工具记录、运行日志和上传上下文可作为一般主张的原始观察来源，须说明其证明范围；它们不能冒充原 Agent 说话者，也不会由此取得受信运行身份。来源角色、引用有效、内容蕴含和来源真实性是四个独立问题。授权、证据适用性和安全保护链继续要求各自的直接比较依据，不能借普通功能反例替代。

声称某断言能区分旧新实现或旧版会失败时，须对同一输入分别推导父版本、目标版本的结果并列出期望值。两版结果相同只能证明该输入的兼容保持；某一反例断言遗漏也不能外推为所有现有断言都无法区分两版。

| 待证明内容 | 可采用材料及最低要求 | 不能替代的材料 |
| --- | --- | --- |
| 用户要求及有效范围 | 当前任务绑定的用户原话或有效决定 | 标题、时间接近、助手推测 |
| 目标代码行为或测试交付 | 目标版本源码、diff 和必要上下文；检查完整相关表达式及边界 | 作者声称已修复、文件名或用例数量 |
| TC12 设计要素 | 可定位的需求、验证计划、配置、测试设计；输入、操作与期望结果应可判定 | 只有测试函数便推定环境和证据计划完整 |
| TC11/TC12 环境前提 | 明确平台、解释器、必要依赖或约定运行前提的计划或配置 | 从语法或函数存在猜测具体环境 |
| 实际执行 | 程序核验的运行回执或等价可信记录，绑定目标版本、源码、测试、日志及具体所需断言 | 测试源码、计划、全绿截图或自报通过 |
| 追加轮次、重开及保留记录 | 可核验的实际流程事件，关联任务、问题、版本及前后状态 | 修复源码、用户希望怎样处理、模型本轮发现问题 |

`source`、`context` 等类型只是最低适配条件；把计划标为 `context` 不会变成执行事实，把上传记录写成 `trusted=true` 不会取得可信身份。助手或工具自述不单独支持确定结论。真实工具输出仍需核对其证明范围、版本和来源。

本轮审计报告的解释也须遵守证据范围。使用“所有测试”“仅有某类输入”等穷尽性描述前，核对完整相关测试文件及分支，并分别记录已定位输入类别与缺失场景。只引用一个列表用例不能推断其他用例也是列表；若存在布尔值等其他输入，应按实际类别描述。缺陷结论和描述准确性分别核查，不以正确总体结论掩盖错误解释。

缺材料、缺日志、缺环境、未检查均不能直接记不适用；缺日志也不能反推从未执行。适用但证据缺失记未核查；程序没有对应可信适配能力时，标记自动检查不支持。当前没有受信流程事件适配的历史动作，不能因上传了过程文字而判满足。

1.8 对原生当前契约的不适用候选独立复核排除范围。单进程中的函数调用仍可跨模块；未新增存储或凭据代码，不能证明受影响调用链没有持久化、外部写入或认证。候选须提供原义务的适用前提、实际受影响范围及可定位的排除证据。排除被反证、范围不完整、引用错误或复核未完成时改为未核查；不由此自动推导满足或不满足，原排除理由和复核记录保留。有效延期、历史契约及上传同名规则不取得原生特殊解释。任务验收的同版本生产源码上下文跨文件时，程序要求 TC04 进入核查；相关代码数量只证明需要检查，不证明契约冲突。

TC07.C03、SEC09.C03 的解决声明候选先仅用原 assistant 原句及同源上下文冻结命题、语气、对象和属性，再独立比较已校验反证。“语法修改完成，接下来运行验证”只陈述编辑事实及未来计划，不能改写为“目标功能已经修复”。语法事实须用语法反证，业务修复声明须用同范围业务反证；无已确认解决声明时保留未核查。实际状态声明须由声明自身的版本元数据或原句目标版本绑定，不能以当前测试失败反向补齐历史状态身份。每批至多两次调用，与其他阶段共享预算。

## 4. 同范围一致性与复检

一致性检查必须绑定**同一任务、同一验收点、同一目标版本、同一判断维度**。任何跨维度影响都需说明具体逻辑，不能机械复制失败状态。

同范围适用必需项出现直接不满足时，整体按失败优先汇总，其余未核查项继续保留。该规则不能向不同对象、不同义务或未建立关系的条款传播：将功能失败关联到安全条件，必须先说明受保护资产、威胁、具体控制及该反例如何使控制失效。普通表格输出错误不能仅凭“保护链失败”措辞升级成安全控制失败；缺这条对应关系时，相关安全条件保留未核查，明确范围不适用则须另有正面依据。

- 必需交付项已证实遗漏，FIX02 的全部必要验收对应不能满足；记录了这个遗漏不能把交付改成满足。
- 一个必需测试缺失可以使对应 TC13 交付覆盖不满足，不能直接据此断言函数实现错误或 TC12 没有完整计划。
- 普通正例测试不满足，不足以证明 TC13.C02 的关键反例缺失。全设计覆盖结论不能成立时阻止无依据的通过；判关键反例不满足仍需对应反例的直接证据。范围或覆盖事实不足则未核查。
- 设计满足不能覆盖实际运行失败；实际测试通过也不能抹去未交付的必需断言或不完整的设计要素。
- 发现缺陷、登记缺口、建议修复、实际修订、实际复检和正式关闭分别记录，不能以“其他地方已经说明”抵消未满足项。

新反例、目标版本变化或原关闭判断错误时，追加关联原记录的新轮次，重开相关问题或标记原结论失效，重新检查原问题及影响范围；旧失败、旧报告和失败尝试保留。暂停、取消、风险接受不转换成已修复。记录完整、修复完成、就绪和正式关闭分别判断；本补充不授予自动正式关闭权限。

上述正式流程义务在 `full_sop` 或正式关闭触发恢复的范围中核查。`code_fix` 且有效确认未请求正式流程时，可报告局部修复、测试与未解决问题，不为取得局部结论补造独立人员、完整关闭清单或批准动作。原正式条件仍列未核定；明确的正式验收或关闭请求、声明，以及含义不清的触发均恢复检查，不能以局部配置回避已作出的正式承诺。

## 5. 派生契约与可追溯产出

每个条件的解释契约保留父条款完整上下文，包括适用范围、满足/不满足/未核查分支及原文定位，并登记契约版本、内容哈希、固定原子项、聚合方式、触发条件、允许证据类型和检查维度。契约的 `I01` 等子项编号是原条件的解释细项，不新增 SOP 条款或原条件 ID。

新审计中，对声明了 `semantic_gate` 且该门槛适用的确定性判断，模型须按契约提供结构化 `semantic_basis`，绑定审计对象、判断维度、依据类型及原文引用；只约束不满足的设计反例门槛，不因此强制其他状态编造反例。缺少该结构时作为响应格式缺项反馈一次，保留同批已通过校验的有效兄弟条件，只重试无效条目；一次修正后仍缺失或校验失败的条目记为 `UNKNOWN`（未核查），保留失败原因与原响应，不提升为满足或转成不适用。此要求只用于新审计或明确的新轮次，不能因旧报告没有该字段而热重判历史结论。

`semantic_basis` 结构正确只证明字段、对象和引用达到程序门槛，不保证其中的因果解释或期望比较语义正确。模型可能把相同原文包装成反证，或提供齐全字段却仍误读要求；因此必须保留成对正反例及失败复测，不能把格式反馈后通过校验当作语义问题已全部解决。

报告分别记录原 SOP 文档版本及哈希、解释契约版本及哈希、程序版本、任务与目标版本、模型候选和程序最终判定。派生解释不得覆盖原文或源哈希；新解释用于新报告或明确的新复检轮次，旧报告不被静默重写。

运行映射采用独立短阶段，输入仅限冻结用户基准与程序已核验身份、完整性及版本绑定的源码、测试及原始运行材料，不携带原助手或工具自述作为可信事实；该阶段完整校验后再派生执行状态。目标运行回执或等价记录通过相应适配器的身份、文件、日志、版本校验后，还须逐份复核其与每个验收点的关系：直接验证、兼容配套、无关或待确认。只有直接验证所选的精确断言参与运行判定，按记录、测试路径、断言行绑定，不能借同文件其他失败传播，也不能遗漏外部审计反例。外部新增断言仍不补成原提交已交付测试。命令、环境、产物及当前身份等证据维度与行为通过独立核查；这些维度的每个满足子项都须有本任务目标版本的有效绑定依据，父条件未核查时也不能绕过。当前本地签名适配器仍须验签，不因证据等价原则跳过既有校验。响应明确截断时按更小子批有界重试，保留已完成兄弟、原响应和预算耗尽记录，不能把分析失败写成业务不满足。

条件状态、失败验收点和问题记录分别计数。多个条件或重叠验收点可能指向同一根因，不能把 22 个不满足条件称为 22 个独立缺陷。根因归组只采用有依据的显式组键；仅同一任务、同一问题类别且声明同一根因的记录可进入候选组，全部原记录、证据和条件关联仍保留。相同文件、引文、验收点或关键词不足以自动合并；实现缺陷、疑似问题和证据缺口不能混为已证实缺陷。显式组仍是候选，缺少可信根因判断时不显示精确独立缺陷数；旧记录无组键时原样逐条展示。

上传规则按上传方明确声明的分项编译，保留完整判定分支；复用 `FIX02`、`TC12` 等相同 ID 不会自动继承本地规则的特殊契约、来源身份或信任。上传的复检、关闭条件同样遵守计划与事实的证据边界。

## 6. 独立正反例与验收方法

以下是边界示例，不是指定实现，也不为任何固定评测样例新增验收要求。

| 独立材料场景 | 应得到的判断 |
| --- | --- |
| 整数解析任务给出具体有效/无效输入与期望结果，验证计划的期望与冻结用户要求一致，并明确 Linux/Python 3.11、前置数据、调用操作、pytest 验证及日志保留方式；目标版本交付全部必需断言，但没有运行回执 | TC12 可以满足；TC13 依据断言内容可满足；实际执行未核查，不能宣称关闭 |
| 同样的完整设计计划，目标测试文件经核实遗漏用户明确要求的无效输入断言 | TC12 仍可满足；相应交付覆盖不满足；若该断言属于明确关键反例，TC13.C02 有直接证据时不满足 |
| 完整设计范围中只有函数和两条断言，没有明确环境或证据采集计划 | 对环境和证据计划子项记未核查，TC12.C01 不能整体满足；不能从存在断言补齐其他要素 |
| 已证实遗漏普通正例断言，关键反例是否齐全尚不明确 | 对应交付覆盖可不满足；TC13.C02 未核查，不能从普通正例遗漏直接判关键反例缺失 |
| 用户明确单平台纯函数任务，材料说明解释器及无额外依赖 | TC11 的适用环境前提可满足；无升级承诺时依具体范围判断升级子项，不强加多平台交付 |
| 仅有修复源码与“已经复检关闭”的说明，没有可核验的轮次及状态事件 | 代码行为可独立核查；流程事实未核查，当前适配能力不足时明示不支持；不能生成追加/重开事实 |
| 完整设计范围中一个六要素条件五项满足、一项未核查；或五项满足、一项有明确违反证据 | 前者整体未核查，后者整体不满足；均不能以多数满足汇总通过 |
| 目标回执记录必需断言失败，其他测试通过 | 对应执行不满足；通过计数不能抵消失败，不正式关闭 |
| 用户明确要求输入 `0` 返回 `0`，验证计划也期望返回 `0`；其他设计要素已齐全，但目标版本还没有测试代码 | TC12.C01.I05 可满足，完整设计可满足；测试交付和实际执行另行核查，缺代码不抹去已有设计 |
| 同一用户要求输入 `0` 返回 `0`，验证计划却期望返回 `25`，输入和版本范围相同且原文可定位 | TC12.C01.I05 不满足；期望虽然可判定，但与冻结需求矛盾，不能借用计划或补丁反向改写需求 |
| 用户要求输入 `0` 返回 `0`，计划只写“验证默认值”，没有明确采用的期望，也没有可核对的反例 | TC12.C01.I05 未核查；不能猜测正确期望已被采用，也不能据缺测试代码直接判设计失败 |
| 一个带适用语义门槛的确定性条目缺 `semantic_basis`，同批其他条件均有效；格式反馈后该条目补齐并通过全部校验 | 有效兄弟结果保留，只修正该条目；修正记录保留，校验通过仍不等于独立证明语义正确 |
| 同样的缺项经一次格式反馈后仍未提供有效 `semantic_basis` | 该条目保留 UNKNOWN／未核查及失败原因，同批有效结果不丢弃，不追加无界修正，不热重写旧报告 |

不适用复核按本原子义务绑定输入、副作用或跳过范围事实。外部响应不能仅因由内部模块返回就视为可信；同步短调用不能排除远端提交和结果未知。普通业务失败不能证明无关 skip 与必验行为有关。明确不适用须有被审对象的正面范围边界；没有实现某机制不证明对应风险不存在。结构化事实仍需真实样本复核，模型自报范围不认证事实。

反证及排除复核每批至多 6 个子项，引用使用原文 quote_id 字符串数组；程序精确展开后继续校验来源、任务、版本和证明范围。不得混用手写坐标或忽略冲突字段。无根因的 null 可规范为空 ID，不因此获得分组。SOP 默认总预算 64 次，重试仍有界；预算或响应失败显式保留未知。

程序确认的失败也允许仅作根因归因，模型不能撤销其失败。跨批仅复用已经验证且未被结果声明门槛否决的根因；ID 定义碰撞不得覆盖。原生接口和数据的直接类型契约子项，在本任务同版本实际生产上下文跨文件时额外复核满足和未核查候选；生产方实际返回与消费方实际使用可以构成隐含合同，无需强加独立设计文档。仅该模式接纳 `compatible_contract`：须有具体合同、期望、实际值及当前目标生产源码的双侧正面兼容证据，只能保留原先已有的满足子项，不能将未知提升为通过、撤销已确认失败或生成失败根因。有效直接反证可改为不满足，证据不足保留未知；类型冲突不能扩为调用顺序、超时或所有生命周期失败。

TC12 完整的扁平父项和原子响应可无损转换为嵌套格式，但缺项、重复、跨条件或混合格式均拒绝，不能替模型补出判断。用户设计来源隔离及原子证据门槛继续有效。

1.9 实测修订：构造方法语义须识别真正的 `__init__` 方法，不能把 `__init__.py` 包文件、目录路径或更长标识符当作实例初始化命题。引用失败的有界重试优先从本阶段可见原文目录选择精确编号，并重新核对事实与理由；不得自动换附近引文沿用错误结论。明确选择的裸 Q-ID 与独立 `quote_id` 对象可以无损展开；完整坐标引用只有原样逐字、坐标精确且来源可见时才允许，重试不自动修正其中任何偏差。不同格式不得混用，任务、版本及语义范围仍须核查。合法引用却缺排除范围证明时保留完成核查的 UNKNOWN；伪造引文、错误任务/版本或格式无效仍登记分析失败，不能用前者掩盖后者。

引用协议统一用于原始任务提取、需求支持复核、基础改动/断言分析、反证、运行映射和 SOP 核查。材料 ID 只定位整份材料，不能直接替代 `run_refs` 等字段中的原文引用。上述阶段均使用相同的有界引用重试和可见目录限制；无正式报告的失败尝试独立保留，不按其它轮次的成功结果补写。

需求复核引用真实用户原话但超出候选所选依据时，属于候选来源需要重建，不属于伪造引文。经完整结构、用户来源和任务边界校验后，携带具体原话诊断退回原有最多两轮的需求提取，并重新复核全部用户要求；不得在复核中直接扩充候选依据、删除该要求或改已冻结基准。第二轮仍不能建立受支持候选时停止且不生成正式结论。标题和目标同样不能把诊断猜测写成已经确认的根因。

原生复合条件的父级说明须从当前原子项重建，即使父级四态标签未变也不能沿用未经逐项支持的旧解释。保留原模型说明用于追踪；未核查理由不能夹带虚构的具体文件内容。观察可以携带本任务验收关联，但只有当前子义务实际要求的事实种类才构成触发证据；外部输入、远端动作和业务失败不能代替必验范围内实际跳过的事实。

TC14 比较及范围复核提供原声明紧邻的前一条工具观察定位，保留任务、原句和观察版本，帮助找到原文而不直接认证陈述。无法唯一定位或绑定不一致时不猜测关联。因果假设的支持须另有可定位的因果机制证据，单独出现 403、异常或测试结果只能证明该次观察结果，不能证明认证发送方式等具体原因。机制引用仍须逐字、同任务及对应观察版本；源码展示可以提供机制候选，字段齐全或模型自报机制不能认证因果真实。

根因标题、触发与机制同样遵守原文证明范围。涉及“仅”“所有”等穷尽性描述时须检查完整相关材料；否则只描述已定位的具体路径。测试遗漏与实现冲突可以分别成立，但不能因总体缺陷正确便保留错误的输入类别说明。

部分主张分析失败与已有局部不满足分别登记。分析影响条件数须包含 `analysis_status=partial`，不能仅统计未知标签或整项失败；同一条件的多条失败事件只计一个受影响条件。此统计只描述分析状态，不改变已保存的业务结果。

原生双侧生产源码的直接合同复核单列 `producer_return_consumer_use` 属性：说明实际返回值、消费操作及数据流。直接冲突或兼容必须三者齐备；证据不足须定位实际缺少的生产侧、消费侧、返回形态、消费约束或流向，缺少独立合同文档不能代替这些事实缺口。原复合条款上下文保留；局部类型冲突不推导其它归属、权限或生命周期均失败，两份文件存在也不证明数据实际连通。

TC14 比较先校验完整且唯一的冻结命题 ID 集，再逐条校验关系、引用及观察版本。合法兄弟项保留，只对无效项在原有最多两次总调用和共享预算内定向重试；缺项或重复 ID 的整份响应不能按行采纳，非法枚举不得自行改成合法关系。确定关系须有同类型、同属性的非空来源依据；已知源码版本须列入对应观察版本，不能因父条件已有有效失败而留下另一个无证的确定主张。针对原观察事件，另一时点的相似工具错误不能代替当前原事件，不能仅凭紧邻位置判定支持。
