# 自检机制方案：本模块相关部分

## 1. 自检要回答什么

对普通使用者而言，自检最终需要回答：这份流程是否说清了要做什么、由什么模块完成、数据如何处理、遇到问题怎么办、如何确认完成，还有什么必须先解决？

自检输出应是有依据的问题与结论。不能仅输出“内容完整”“建议完善错误处理”或一个模型自评分。

技术摘要适合快速介绍；模块、运行场景、决定、质量与风险仍需展开。这个划分借鉴 [arc42 方案概述](https://docs.arc42.org/section-4/)及其[运行场景](https://docs.arc42.org/section-6/)。

### 1.1 三层检查与证据边界

| 层次 | 检查对象及方法 | 可支持的结论 | 不能由此推出 |
| --- | --- | --- | --- |
| L1 结构检查 | 字段、ID、引用、版本、依赖、关联格；采用可重复程序规则，核查误报 | 规定的结构规则满足或不满足 | 设计合理、核心方案可行、功能实际通过 |
| L2 语义复核 | 需求含义、模块职责、接口双方、数据/状态、任务/验收一致性；逐条追踪、资料查证及独立复核 | 在声明范围内有依据的设计判断或具体冲突 | 模型无误、试验完成、用户批准 |
| L3 可行性查证 | 核心假设所需的平台、版本及实际环境依据；官方资料和必要的原型/操作/文件/日志核查 | 对明确假设取得相应依据；实际试验单列通过/失败/未验证 | 最终产品、其他平台或所有未来情况已通过 |

每条规则指定需要哪些层次。官方资料可支持它明确说明的版本事实，不能证明本项目实现已成功运行。规则要求实际试验而未执行时，不能因已有试验计划计满足。

检查状态为 **满足 / 不满足 / 未核查 / 不适用＋理由**；实际试验状态为 **通过 / 失败 / 未验证 / 不适用＋理由**。两者分列，不将“设计满足”显示成“产品通过”。

### 1.2 来源事实与本项目规则

arc42 提供文档划分和代表性场景方法；NASA 提供设计审查、需求追踪和原型验证指导；MADR 提供技术决定记录结构；Google SRE 提供有实际动作、可裁剪的准备检查方法。来源支持方法，**不共同规定本文件的检查编号、严重程度、状态流和停止条件**，这些是本项目建议。用户批准与项目预算也不能从资料推导。

Google SRE 方法见[发布准备原文](https://sre.google/sre-book/reliable-product-launches/)；各来源的版本及本项目采用范围见参考资料索引。

不要求所有应用具备取消、重试、升级或全部异常场景。适用范围由已确认目标、实际能力和风险决定；不适用要留理由，关键风险不能为提高分数删除。

### 4.1 适用性与具体满足条件

下表补充上表。每个项目开始检查时固定对象清单和适用项；子项不适用记录理由，不能因缺数据或缺环境移出分母。纯本地小应用可合并模块/数据记录，无需套用云系统组织结构。

| ID | 适用性 | 具体满足条件 |
| --- | --- | --- |
| TC01 | 所有项目 | 对象/规则版本和范围可定位；有效决定、目标平台明确；草案/已确认分开，基线冲突不隐藏 |
| TC02 | 所有项目 | 每条适用需求有内容正确的设计、任务、验收关联；设计反向有需求或交付目的；缺口/孤立对象有处理记录 |
| TC03 | 所有项目；层次按规模 | 职责、边界、输入输出、数据归属、依赖、失败责任清楚；必要动作无无人负责或冲突负责；依赖满足声明约束 |
| TC04 | 跨模块/进程/文件/服务边界；无独立边界要说明 | 双方输入类型/约束、输出、错误、权限和版本一致；适用调用顺序、超时/重复/兼容行为明确；关键未知转 TC07 |
| TC05 | 数据必查；持久化/敏感数据/迁移按范围 | 类型、约束、归属、生命周期、读写明确；需保存时有失败保留/恢复；需删除/迁移时有范围/后果；关键假设取得所需依据 |
| TC06 | 正常关键操作必查；其他场景按能力及风险 | 适用场景有前状态、事件、状态/数据变化、可见结果和失败责任；关键可达状态无未说明出口；不支持的行为有明确边界 |
| TC07 | 所有项目先识别未知；关键假设需查证 | 未知分类、影响与下一动作明确；影响核心实施的假设取得事先要求的资料或实际试验依据；失败/未验证不算解决 |
| TC08 | 已声明及范围必要的质量约束 | 触发、环境/规模、响应、判断方法明确；数字有单位/来源；无依据登记待决定/待测，不自行编造阈值 |
| TC09 | 权限/副作用必查；凭据/外发按实际能力 | 信任边界、必要权限、数据流和保护/生命周期明确；副作用在有效决定内；新增或未知权限不默许 |
| TC10 | 使用外部库/工具/服务/复用代码时 | 版本、许可义务、目标环境、关键限制可查证；关键依赖失效有影响和可行处理；低风险依赖不强制备份技术栈 |
| TC11 | 交付环境必查；安装/升级/回退按范围 | 各平台运行/交付前提明确；适用兼容、失败和恢复行为具体；环境缺口保留；首版未承诺升级需说明边界 |
| TC12 | 全部适用验收×平台组合 | 前置、环境、数据、操作、可判定断言、证据计划齐全；自动/人工方法与观察能力一致；缺环境仍有设计，真实运行另列 |
| TC13 | 全部验收设计与关键试验 | 断言验证原需求行为/结果；关键反例按风险覆盖；不以文件、按钮或实现存在代替功能完成 |
| TC14 | 外部依据与继承证据；本地决定亦绑定版本 | 来源/版本/日期/位置及适用性明确；主张不超出资料；冲突/失效保留；依据复用有影响评估 |
| TC15 | 所有发现；无发现亦需复核记录 | 问题有影响、状态、下一动作；关闭有依据和复检；变更/反例触发重开或失效评估；暂停/取消不算关闭 |

每条检查按 L1/L2/L3 分别留结果；所需层次未完成时，不把其他层的满足当成整项满足。凭据检查的报告应脱敏，不能为了定位问题复制真实秘密。

层次建议：TC01/TC02/TC03/TC12/TC14/TC15 以 L1 和 L2 为主；TC08/TC09/TC10/TC11 以 L2 为主，结构字段可另做 L1；TC04/TC05/TC06/TC07 除设计复核外，按关键假设决定是否需要 L3；TC13 以 L2 为主。具体对象已有有效资料可回答事实时不强制试验；必须依赖目标环境证明的假设不能省去 L3。


## 5. 问题台账与关闭标准

每条问题记录：问题 ID、检查 ID 与层次、对象版本与位置、预期规则、实际发现、依据、影响对象/任务、严重程度与理由、是否阻塞及理由、处理类型、需要谁处理、下一动作、结束条件、状态、修改前后、复检结果与证据、历史。

问题状态：**待处理 → 查证中 / 待用户决定 / 环境阻塞 / 修订中 → 待复检 → 已关闭**。分流可以调整；失败或依据不足返回待处理或相应阻塞状态，保留尝试历史。

**已关闭的最低条件：** 原问题有具体修订或查证结果；依据支持对应结论；关联检查满足；受影响对象已复核；需要确认的变化已有有效确认。删除问题行或把状态改成“已处理”不满足关闭条件。

每个来源的完整摘要不必重复抄入问题卡，引用来源 ID 和准确位置即可。

关闭依据按问题类型选择：无效引用修复用当前文件的引用核查；设计冲突修订用契约/语义复检；实际可行性失败用规定的目标环境重测。文档问题不一律要求运行应用，实际试验问题也不能仅凭改文档关闭。

TC15 检查台账和处理/复检记录是否真实、完整、符合当前状态，**不是要求所有问题均已关闭**。诚实保留未关闭问题、下一动作和阻塞可以满足对应审计记录项；事先要求完成但尚未执行的修订/复检项仍不满足或未核查，相关任务仍未就绪。记录合规、处理完成、项目就绪分别汇报。

### 5.1 严重程度与相关任务阻塞

| 等级 | 判定依据 | 处理建议 |
| --- | --- | --- |
| 关键 | 违反有效需求/权限决定；核心方案不可实施或依赖未查证关键假设；可能造成重要数据损失/越权；基线冲突使执行对象不明 | 阻塞受影响任务及其实际依赖；需求/方案/权限变化提交用户决定；跨阶段基线问题可能影响整个阶段 |
| 重要 | 接口、数据、状态、验收等有具体缺口，使相关实现不能据此可靠完成或评判，但影响可定位 | 阻塞依赖该缺口的任务；独立部分可继续，留下依赖边界和理由 |
| 一般 | 表述、维护或非关键细节问题；已有明确设计及依据，当前任务仍能按要求完成 | 留修订安排和允许推进的理由；若属于用户确认的必需门槛仍阻塞 |

等级依据实际影响，不按关键词或单个模型分数自动决定；未授权的新权限/副作用不能降级后继续。事实不足可标“严重程度待判断”，关键风险相关部分仍未就绪。

阻塞范围从问题定位到需求、模块、接口、数据、平台和任务，再沿实际依赖传播并说明理由；不要仅因同属一份文档阻塞无关任务。影响范围不明时登记分析缺口；不依赖该问题的资料整理、设计复核或其他已授权工作可继续。解除阻塞须记录当前版本复检与有效确认的依据。

### 5.2 状态变化、重开与误报

| 变化 | 必要记录与边界 |
| --- | --- |
| 待处理→查证/修订 | 下一动作、责任、授权/预算和结束条件；开始处理不等于解决 |
| 处理状态→待复检 | 实际修订或查证结果、差异、影响范围和证据；生成建议不等于关闭 |
| 待复检→已关闭 | 原问题得到回答、依据适用、原规则满足、相关对象重检、必要确认有效 |
| 已关闭→重开 | 新事实/反例、版本变化或关闭判断错误；新一轮关联旧记录并回到待处理/相应分流，不覆盖原关闭历史 |
| 本轮暂停/取消 | 保存原因、未解决项、成果、额度使用和恢复条件；这是轮次状态，不是问题关闭 |
| 复核为误报/重复 | 保留规则、事实、范围理由或关联原问题及复核记录；不能用“非问题”掩盖尚未回答的缺口 |

可拆分关联问题：“缺少可行性试验计划”与“关键技术假设未验证”。前者补全设计后可复检关闭；后者必须取得所需依据，不能因计划完善一起关闭。

### 5.3 版本影响与证据有效性

检查、问题、来源、试验和决定绑定对象版本、平台与环境。同名文件改动后，不能继续默认沿用原检查结果。

| 变化 | 影响评估与复检 |
| --- | --- |
| 文案/定位调整 | 核对是否仅改变表达，不改变行为、条件、边界或承诺；保留差异与理由，不自动要求全部试验重跑 |
| 接口/数据/状态/依赖变更 | 追踪调用方、消费者、场景、任务及验收；受影响结论待复检，实际试验按影响重做 |
| 需求/方案/权限实质变化 | 新内容待确认；保留原版本和决定；取得相应阶段确认后推进相关执行 |
| 平台/环境/依赖/规则版本变化 | 重新判断适用范围与支持的结论；新平台不继承另一平台的实际通过；规则变更重算相关口径 |
| 新资料推翻旧依据或发现遗漏 | 保留冲突、影响与重开理由，按最新有效基线复检 |

设计结论、用户确认和实际证据分别判断有效性。旧依据可在有记录的影响评估后复用，旧实际执行记录仍保留原版本/环境；不改写成新一轮通过。部分不受影响不代表整个新基线已就绪。

### 5.4 预算、停止与恢复

本轮停止条件包括：适用检查已完成并报告；需要用户决定；有效调用/输出/时间/费用/资源限制到达；下一动作无法保证在剩余额度内；同一关键问题按有效停止规则重复处理却无新依据；用户暂停/取消；关键前提失效。

具体次数、重试与费用限制来自有效授权，本方案不自定付费上限。失败请求、重试和其他调用如何计次/计费按授权口径与服务记录核对；口径不明不假定免费或不计次。达到限制保存候选成果、问题、尝试历史和停止原因，不无限重试。本轮没有调用用户配置的模型 API。

恢复时读取停止记录和最新基线，检查决定、权限、环境、预算是否仍有效；核对剩余额度；分析变更影响并重检失效项。过期预算不自动续期，取消后的成果也不自动代表恢复已获授权。没有目标环境的关键试验仍未验证。

报告列出基线/规则版本、适用与不适用范围、分层结果、量化分母、问题和影响任务、真实试验/平台缺口、待决定、预算及下一动作。建议相关任务就绪条件为其阻塞项解决、适用必需检查满足、核心假设取得所需依据及当前阶段确认有效；正式门槛须用户确认。报告记录满足不代表所有修订或试验均已完成。
